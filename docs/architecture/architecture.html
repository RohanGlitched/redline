Redline how a change order is checked and held
Runs on Atlassian: no egress, no remote backend, no AI service. Drawings never leave Atlassian.

Change order in Jira

  • Rev C and rev D drawing PDFs, attached
  • A phone photo of the printed drawing with the machinist's red pen
  • Change notes in the description: "1. Zone D2: bore Ø25 becomes Ø25.5"

In the reviewer's browser (Forge Custom UI)

1pdf.js renders both revisions and reads their text
2Register rev D onto rev C, diff the line work, cloud each change with its drawing zone
3Match each change to a numbered note; check the values both ways; check the title-block revision letter
4Flatten the photo onto rev D and separate pen red from printed red

Plain JavaScript engine, no dependencies. A person declares, answers and signs off each line.

Forge functions

  • Save the review: signers named by Jira, never drops a change found earlier, audited
  • Write a missing note into the description
  • Raise a pen markup as a work item

Triggers keep the index current and clean up on delete.

Forge app storage

Review, audit log, verdict index (KVS)

attachments and change notes, read live by every check
One verdict, shared/gate.mjs, computed the same way in the browser and in every Forge function below

Release gate

A workflow validator refuses the release transition until every change is declared, matched, signed off and every markup answered. It reads app storage and fails closed.

Dashboard gadget

The change orders Redline is holding, why, and since when.

redlineGate = "blocked", from an entity property.
